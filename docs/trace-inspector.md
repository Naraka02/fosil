## Projection and correlation

Trace reads the same validated selected-session event prefix as Chat and performs no network request or command of its own. Its pure evidence projection retains runs and steps by their recorded identities, creates one user item per saved message, and correlates one assistant record per model request identity, one tool record per call identity, and one approval record per approval identity. A separate message projection presents only `SYSTEM`, `CONTEXT`, `USER`, `TOOL`, and `ASSISTANT` rows. It places the first request's initial instructions and exact tool schema list in one `SYSTEM` row, presents each distinct system-role request message as Agent-supplied `CONTEXT`, and omits approval as a standalone message while retaining it in the correlated tool details.

The initial `SYSTEM` row precedes the first Turn even though the prompt becomes durable with the first model request. The remaining visible messages follow ascending canonical start sequence, with new `CONTEXT` placed immediately before the assistant result for the request that first carries it. Repeated request snapshots do not repeat identical context. Sequence numbers, start and finish timestamps, attempts, terminal reasons, and recorded statuses remain available in details; an unfinished record keeps a live sequence boundary and a pending finish time.

A settled model request or tool call supplies the record's primary status and output. Model deltas remain separately folded stream evidence and are not appended to the final output. Model records expose Context Composition first, including the locally measured request, source contributions, dispositions, and tool-result pruning, then expose the exact saved settings, system instructions, messages, and tool schemas separately from text and reasoning output, stop reason, error, timing, and provider usage. Tool-call fragments are represented by a count rather than repeated payloads because the correlated tool record owns those arguments and results. An earlier event without composition shows an explicit compatibility notice while retaining its exact request. Tool records expose the request and provider-call correlation, frozen arguments and working directory, approval identity, canonical result, error, timing, exit code, and evidence. Approval records expose the gated call, requested arguments, policy, expiry, decision, source, and measured wait.

Null usage, timing, exit, or other measurements render as `Unknown`; zero remains zero. Trace does not estimate missing measurements or infer reasoning that was not retained.

## Inspection behavior

The DSH-style full-width ledger is a single top-to-bottom message timeline. Each compact row has only two visual columns: a fixed-width uppercase message type on a restrained colored background and one single-line information flow on the right. `SYSTEM` is introduced as `Initial System Prompt` and names its available tools; `CONTEXT` shows a content summary; `USER` shows the saved user content; and `TOOL` leads with the executed tool name before its argument summary, arrow, and result summary without field labels. A normal `ASSISTANT` row shows retained result content. When the model requests a tool, the `ASSISTANT` row shows saved pre-call reasoning, then pre-call text only when reasoning was not retained, and never renders the tool-call block. Tool-call payloads are likewise omitted from the assistant inspector because the correlated `TOOL` row owns their execution presentation. Compact Turn and Request identifiers hang from the corresponding row boundary without becoming part of the row's message content. Turn uses a larger filled blue marker and stronger weight, while Request uses a smaller muted outline so the conversation boundary dominates the individual model-call boundary. Step and sequence metadata do not occupy the ledger.

Selecting any row opens its correlated details in an on-demand right-side inspector instead of permanently reducing timeline width. A user row exposes its saved command identity, run approval mode, and exact message; system and context rows expose the complete retained input; tool details include correlated approval evidence; and assistant details retain the exact request plus saved text and reasoning response evidence without duplicating tool-call payloads. The top-right close control lives inside the sticky inspector header, remains fixed while the detail body scrolls, has a visible surface plus hover, pressed, and keyboard-focus states, receives focus when the inspector opens, and supports both activation and `Escape`. Closing the inspector returns to the full timeline. The errors-only filter retains failed, denied, cancelled, interrupted, expired, explicitly errored, or unknown-evidence tool and assistant outcomes and omits informational message rows.

Saved `file_change` evidence receives a dedicated diff panel. Other evidence remains labelled JSON and is not presented as an attributable workspace change. JSON values are rendered as text, and the application loads no external visual resource.

## Payload flags and limits

Trace surfaces explicit retained fields whose names identify truncation, masking, omission, invalid encoding, or incompleteness. A recorded `false` remains visible. Absence of a matching field means only that no explicit flag was retained; it does not prove completeness or absence of sensitive content.

The application still loads a complete selected-session prefix of bounded browser projections into memory and has no payload export, recovery-blocker resolution, payload search, virtualization, or large-session performance guarantee. Explicit record deletion belongs to [Chat controls](chat-controls.md#command-behavior) and removes the corresponding Trace source rather than editing Trace independently. Configured-secret masking, shared content metadata, retained-payload budgets, and the product launcher are implemented at their owning service boundaries. Arbitrary shell changes remain unknown evidence rather than automatically attributed diffs.
