# Chat controls

Document type: reference.

This reference owns the implemented browser Chat workflow, its event projection, mutation behavior, and current product limits. The [Trace inspector](trace-inspector.md) owns detailed execution presentation; the [HTTP service](http-service.md) owns routes and browser-origin enforcement; the [event contracts](execution-events.md) own lifecycle facts; the [product scope](product-scope.md) owns release requirements. ## Available workflow

The built Simplified-Chinese React application lets a local operator browse and select an existing local directory as a workspace, create a session from that absolute Linux path, select a saved session, submit one message when that session has no active run, follow committed assistant text and tool summaries, resolve a pending allow-once approval, and request cancellation. It displays service and stream state and adapts the same workflow to desktop and narrow browser viewports. Its visual shell follows the fixed DSH reference geometry: a 336-pixel desktop workspace sidebar, outlined new-session action, tabbed session header, open reading column, floating composer, and large settings overlay. Desktop navigation can collapse to an icon rail; a narrow viewport replaces it with an explicit drawer.

The application is served only when the caller gives `ExecutionHttpServer` a valid browser build directory. The [product launcher](deepseek-provider.md#product-launcher) supplies that build, the DeepSeek execution model, local database, and masking configuration. Chat and Trace switch over the same selected-session history.

## Saved-state projection

The client treats schema-valid browser event projections as its only conversation state. Selecting or reopening a session reads every page of one fixed canonical prefix through the [bounded HTTP projection](http-service.md#http-interface), projects its runs, messages, model requests, tools, approvals, measurements, and terminal states, then opens EventSource strictly after the loaded sequence. Within each run, assistant turns and tool calls share one durable activity order: a tool remains immediately after the assistant turn that created it, carries its event step, and keeps its later result or error in that same disclosure. A pending approval is rendered beside its correlated tool rather than at the run's end. Session list refreshes do not decide whether an approval is actionable or a run is complete.

An incoming event must pass the shared schema and extend the selected session by one sequence. An exact repeated event is ignored. A gap, cross-session event, or conflicting duplicate closes the stream and rebuilds the projection from durable history. A finished model request replaces its accumulated text deltas, so live and reopened output do not concatenate the same response twice. Reasoning content and complete Trace payload inspection are not presented by Chat.

Only an unresolved `approval.requested` without a later `approval.resolved` produces action buttons. Tool and run settlement removes those controls through the same event projection. Refresh reads history and reconnects; it does not infer or reissue a command.

## Command behavior

Each explicit click creates one random command identity and sends one POST. The client never automatically retries a session creation, submission, approval decision, or cancellation. While a command is in flight, related controls are disabled. After acceptance, submission, approval, and cancellation controls remain guarded until their canonical event becomes visible.

The composer exposes `手动审批`, `Workspace Write`, and `Full Access` before submission through a DSH-style toolbar trigger and upward menu rather than a native select. The menu shows the current choice, a concise consequence for every mode, a distinct high-risk marker for Full Access, and the durable-recording boundary. It closes after selection, outside interaction, or Escape and fits the narrow composer without horizontal overflow. The selected browser preference is sent with `run.submit`; once accepted, the trigger is disabled and shows the active run's persisted mode rather than a mutable browser override. The first transition to Full Access requires an explicit warning confirmation that Shell may read or modify paths outside the workspace, start processes, or cause other host effects. Cancelling that dialog preserves the previous selection. The [tool-execution reference](tool-execution.md#approval-progression) owns the enforcement semantics and their confinement limits.

If a mutation has no trustworthy HTTP outcome, the browser reports that delivery may be uncertain, disables further mutations, and asks the operator to refresh and reconcile saved history. A validated HTTP rejection remains a definite error and does not lock unrelated controls. This favors duplicate suppression over guessing that a missing or invalid response means the command was not committed. The durable receipt and service retain their [existing exact-retry semantics](event-store.md#commands-and-receipts), but this Chat slice does not expose a manual receipt-retry control.

## Presentation and limits

Chat renders user text through React text nodes and renders assistant output as CommonMark plus GitHub Flavored Markdown using local React components. Headings, emphasis, lists, task lists, blockquotes, links, tables, inline code, and fenced code blocks are supported. Raw HTML is not injected, Markdown images become textual placeholders instead of network requests, and links open in a separate context with opener isolation. Tool arguments, browser-projected results, and errors are formatted as JSON or text inside their step-correlated disclosures. A pending decision uses the DSH approval hierarchy: a flat amber operation boundary, explicit action title, working directory, bounded argument block, durable-event note, and deny/allow-once actions. The UI loads no external visual resources.

The composer ends with one compact measurement strip for the most recent run, containing its one-based conversation round, distinct started-step count, total model-call duration, total tool-call duration, average first-content latency, output throughput, cache-hit rate, and input/output token totals. Keeping the strip inside the composer makes the current run's operating evidence visible without adding repeated rows to conversation history. Output throughput divides saved output tokens by summed model duration minus summed first-content latency. Cache-hit rate divides saved cache-read tokens by saved input tokens. A total is shown only when every contributing saved model or tool measurement is known; a missing contributor renders as an em dash rather than an estimate. A run without a tool call has a known zero tool duration.

The interface uses one selected session and one SSE connection. Its active Chat surface owns the remaining main-area height, keeps conversation history in an independent scroll container, and reserves the composer as a non-scrolling bottom row. The composer therefore remains visible while long content scrolls above it; the idle-session focal composer retains its separate centered positioning. The application loads every lexical storage page, then groups sessions by exact workspace root and orders both workspace groups and sessions by the latest durable event timestamp descending. Equal timestamps use stable workspace-root and session-identity tie breaks. The new-session action and workspace-heading add action open the same local directory picker; confirming its current absolute path creates a session, and only that durable session causes a workspace group to appear. The picker keeps manual absolute-path input as a fallback and does not create folders or retain a second browser-owned workspace catalog. The [HTTP service](http-service.md#http-interface) owns its read-only discovery boundary.

The sidebar and selected-session header display the store-provided title derived from the first durable user message and refresh it after the accepted first submission. The browser does not call a model to name sessions and exposes no rename, deletion, search, or date-grouping behavior; the [event-store reference](event-store.md#session-discovery) owns normalization, truncation, fallback, and persistence semantics.

An idle selected session uses the DSH-style centered creation surface and moves the same real composer into the focal position; a session with runs uses the persistent top tabs and bottom composer. The settings modal follows the reference scale and navigation but contains only a local sidebar-collapse preference and read-only runtime facts: service phase, selected-session event connection, launcher model, selected workspace, and selected session. Approval mode remains a per-submission composer control; settings do not expose provider creation, plugins, presets, attachments, or per-turn model selection. The concentric Fosil mark is code-native SVG and the browser loads no remote font, icon, or image resource.

Chat does not expose complete model request context, reasoning, tool evidence, diffs, individual-call measurement detail, or retained-payload flags; its tool result and aggregate run statistics come from the bounded browser projection rather than the canonical retained payload. The separate [Trace view](trace-inspector.md) presents detailed browser-projected facts where implemented. Recovery blocker resolution, session deletion, export, and hostile local-process isolation remain unavailable. Configured-secret masking and retained-payload budgets apply in the service, not as Chat-side heuristics.

## Verification

Run `npm test -- packages/server/src/chat-browser.test.ts packages/web/src/chat-model.test.ts packages/web/src/Markdown.test.ts` after installing the [development prerequisites](development.md#setup-and-verification-procedure). The projection tests check final-versus-delta replacement, assistant-tool ordering across steps, correlated tool results, pending approval reconstruction, complete-versus-unknown measurement aggregation, token throughput and cache-hit calculations, exact duplicate delivery, sequence gaps, conflicts, and cross-session input. The Markdown tests check supported block and inline structures plus raw-HTML and image suppression.

The browser test builds the application and uses real Chromium, loopback HTTP/SSE, the production agent loop, SQLite, a controlled provider, and an approved Shell fixture. It checks the three approval-mode choices and the Full Access confirmation before returning to manual mode, observes committed streaming text, refreshes before and after allow and deny decisions, proves the approved marker is written once and the denied marker is absent, cancels a waiting provider and observes its cleanup, reopens the cancelled run, checks a 390-pixel viewport for horizontal overflow, and refuses external resource requests. This Chat evidence does not establish a real model, hostile-process confinement, sensitive-repository handling, or large-session performance; the [Trace verification](trace-inspector.md#verification) owns its separate evidence.
